# Проверки CI

**Русский** | [English](README.en.md)

## GitHub

Контролируемое сравнение 1/2 worker запускается отдельно и вручную:
[методика и действия владельца](comparison.md). Это не часть обычного push CI.

[CI](../.github/workflows/ci.yml) запускается на push любой ветки/тега,
pull request и вручную. Два независимых задания на `windows-latest`:

- Validate (5 минут): обязательные файлы, синтаксис PowerShell, формат версии,
  категории CHANGELOG и структура/трассировка ТЗ (`--strict`, Python 3.12).
- Regression (30 минут на оболочку): все `tests/Test-*.ps1` в Windows PowerShell
  5.1 и PowerShell 7. Матрица не отменяет вторую оболочку при отказе первой.

В каждом задании регрессии создаётся снимок checkout и запускается
Invoke-Isolated с двумя worker, без выбора подмножества тестов. Бюджет runner
25 минут, набора 10 минут; остаток лимита job оставлен подготовке и выгрузке.
Каждому набору выделены собственные исходники, cwd, TEMP/TMP и дерево процессов.
В артефакт входят manifest.json, run.json, results.json и логи наборов,
но не рабочие копии исходников и сгенерированные тестовые файлы.

Логи каждого набора, время, код возврата и `results.json` загружаются даже при
ошибке; артефакты `test-logs-powershell` / `test-logs-pwsh` хранятся 14 дней.
Новый штатный `Test-*.ps1` включается автоматически; `tests/manual` не запускается.
Тесты используют заглушки, не требуют оборудования и не подтверждают работу на MCU.
Регрессии проверяют CMD-запуск, движки, RU/EN, конфигурацию, безопасность и упаковку.

## Локально

Для тестов снимка также нужен Git в PATH. GitHub устанавливает Python 3.12
в каждом задании регрессии; дополнительных пакетов Python не требуется.

Нужны Windows, обе оболочки и Python 3.12 в PATH. Из корня клона:

```powershell
./ci/Invoke-Local.ps1
./ci/Invoke-Local.ps1 -Stage Validate
./ci/Invoke-Local.ps1 -Stage Regression -PowerShellExe pwsh
```

Первый вызов выполняет статические проверки и обе оболочки последовательно.
Это полный локальный прогон; один `pwsh` не заменяет матрицу PS5.1/7.
Можно задать `-PythonExe` и `-PowerShellExe` полными путями.
Не найденная оболочка или Python означает ошибку, а не пропуск проверки.
Ненулевой результат набора не скрывается, остальные наборы продолжают выполняться.
Статическая ошибка останавливает полный прогон до регрессий.

Логи по умолчанию: `tests/.tmp-ci-logs/<дата-время-id>/1-powershell` и `2-pwsh`,
Git их игнорирует. Каждый локальный вызов сохраняется отдельно. Явный
`-LogDirectory` сохраняет прежнее поведение: повторно использует указанный путь;
для независимых попыток задавайте разные каталоги. Для отдельного теста:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/Test-Localization.ps1
pwsh -NoProfile -File tests/Test-Localization.ps1
```

`tests/Invoke-Tests.ps1` остаётся совместимой точкой запуска одной оболочки.
GitHub использует те же скрипты из `ci`, но запускает оболочки в отдельных jobs.
Полный прогон занимает несколько минут; по длительности одного набора нельзя
судить о зависании. Живой вывод и логи показывают текущий этап.

## Снимок исходников

Перед распараллеливанием: [аудит изоляции и методика сравнения 1/2 worker](isolation.md).

```powershell
./ci/Invoke-Snapshot.ps1 -Kind WorkingTree -Profile Quick
# Полный прогон чистого HEAD перед интеграцией:
./ci/Invoke-Snapshot.ps1 -Kind Commit
```

WorkingTree включает текущие байты отслеживаемых и новых неигнорируемых файлов,
учитывает удаления. Commit требует чистого дерева и использует `git archive HEAD`
(включая правила export-ignore/export-subst). Это разные виды входа, указанные
в манифесте. `.git`, игнорируемые логи, прошивки и кэши не копируются.
Неигнорируемый личный файл попадёт в WorkingTree: проверьте `git status` заранее.
Symlink, junction и submodule требуют отдельной схемы и сейчас отклоняются.

Во время создания не редактируйте исходники: повторное чтение обнаруживает
изменение состава/байтов и отменяет запуск. После создания можно работать
в исходной папке: проверки выполняются только в отдельной копии `source`.
Это не атомарный снимок файловой системы и не песочница для недоверенных тестов.

Каждая попытка получает новый `tests/.tmp-ci-snapshots/<время-id>`:
`source.zip`, `manifest.json` (HEAD, dirty, UTC, SHA-256 каждого входа и ZIP),
`source`, `console.log`, `logs`, `outcome.json` (параметры, версии, статус,
целостность и длительность создания/проверок/контроля). Время проверок включает
получение версий процессов. Можно явно задать новый `-RunDirectory`; существующий
каталог не переиспользуется. Ошибки и незавершённые попытки не удаляются;
Creating/Running не означают успех. Чистота копии проверяется до и после запуска;
изменение входа, архива или манифеста означает отказ. Новые файлы допускаются
только в `tests/.tmp-*`, `tests/manual`, `docs/research`, `dist`, `__pycache__`;
существовавшие входы проверяются по SHA-256 и там. Защита от случайных изменений,
а не от кода, намеренно подделывающего результаты.

`-Stage`, `-Profile`, `-TestName`, `-PowerShellExe`, `-PythonExe` передаются
локальному CI. Full остаётся умолчанием; Quick и выбор наборов дают частичное
покрытие, см. `logs/*/run.json`. Полный GitHub CI не сокращён.

## Изолированный runner (opt-in)

Windows-only; обычный локальный запуск остаётся последовательным, GitHub использует
два worker. Создайте свежий снимок с текущим runner и проверьте статику:

```powershell
$snapshot = Join-Path $PWD.Path 'tests/.tmp-ci-snapshots/parallel'
./ci/Invoke-Snapshot.ps1 -Stage Validate -RunDirectory $snapshot
./ci/Invoke-Isolated.ps1 -SnapshotDirectory $snapshot -Workers 2
# Для сравнения на тех же входах:
./ci/Invoke-Isolated.ps1 -SnapshotDirectory $snapshot -Workers 1
```

Умолчание Workers=1. Без TestName запускаются все Test-*.ps1; точный выбор
и -List поддерживаются, частичный прогон помечается явно. PS5.1 и PS7 идут
последовательно; внутри каждой оболочки одновременно работают до двух наборов.
Свободный worker берёт следующий набор. Каждому выделены отдельные исходники,
cwd, TEMP/TMP и Windows Job Object. После выхода основного процесса даётся
до одной секунды на завершение дерева; оставшиеся потомки принудительно
завершаются и считаются ошибкой. Исходное число процессов и длительность
ожидания сохраняются. Это изоляция случайных конфликтов, не песочница недоверенного кода.

Таймаут набора: -SuiteTimeoutSeconds 600; общий бюджет одной оболочки:
-RunTimeoutSeconds 1800 (включает подготовку, проверяется между этапами
и во время исполнения). Отмена/общий таймаут останавливают активные деревья
и очередь, возвращают ошибку и не запускают следующую оболочку. Обычная ошибка
набора не отменяет остальные. Прерванный или неполный прогон не бывает Passed.

Логи сохраняются в новом tests/.tmp-ci-isolated/<id>/<номер-оболочка>.
Явный -LogDirectory тоже должен быть новым; старые результаты не затираются.
run.json/results.json содержат состав, частичность, длительности и итог;
нумерованные подкаталоги содержат копии, stdout/stderr, логи и result.json.
Снимок и копии проверяются по SHA-256 до/после. Нулевого exit code без
согласованных результатов недостаточно. Вывод общего runner показывает
завершение наборов; подробный текущий вывод находится в их логах.
Сравнивайте 1/2 worker на одном снимке, без других тяжёлых запусков.
Код runner должен совпадать со снимком; старый снимок без него не подходит.

## Контрольные измерения

После окончания тестов, без других прогонов CI, укажите каталог снимка:

```powershell
$run = 'tests/.tmp-ci-snapshots/<время-id>'
python -B -X utf8 "$run/source/ci/benchmark.py" --snapshot $run
```

Windows-only benchmark запускает последовательно PS5.1/7 напрямую и через CMD:
пустой процесс и чтение/синтаксический разбор сохранённого `flash.cmd`, без его
выполнения и доступа к MCU. Для каждой комбинации: 2 прогрева, затем 2 серии
по 8 измерений; порядок перемешан с фиксированным seed, вторая серия зеркальная.
Прогрев не входит в статистику. Параметры: `--warmup`, `--rounds`, `--repeats`,
`--seed`, повторяемый `--host`. Запускайте именно сохранённый benchmark.

Отдельный `benchmark-*.json` содержит все пробы, версии, параметры, SHA-256
манифеста/benchmark, медиану и диапазон каждой серии. Код ошибки/таймаут 30 с
останавливает измерение с Failed, прежние пробы сохраняются. Итог проверяет
целостность снимка. Сравнивайте серии на одинаковых входах и машине; это оценка
расходов запуска/разбора, не ускорение полного CI. Локально параллельность opt-in.

Контрольный опыт 11.10.2026 (PS5.1.26100.9444 / PS7.6.6, Python 3.11.9):
медианы двух серий пустого процесса — 99/103 мс напрямую и 669/655 мс через
CMD для PS5.1; 150/150 мс и 703/697 мс для PS7. Разбор добавлял примерно
20–60 мс, CMD — около 550 мс. Это наблюдение одной Windows-машины, не норма
производительности и не установление причины задержки (например, антивируса).
Локальный опыт не заменяет проверку Python 3.12 в GitHub.

## Выбор наборов

```powershell
./ci/Invoke-Local.ps1 -Profile Quick -List
./ci/Invoke-Local.ps1 -Profile Quick
./ci/Invoke-Local.ps1 -TestName Test-Localization.ps1,Test-TestRunner.ps1
```

Quick включает статику и шесть коротких наборов: Ci, ExplicitSerial, Localization,
ProbeInventory, ReleaseNotes, TestRunner. По умолчанию обе оболочки. Это проверка
инфраструктуры и отдельных контрактов, а не smoke всех команд прошивки.
Для правки только документации начните с `-Stage Validate`; для изменения рабочего
кода добавляйте затронутые наборы. Quick не заменяет CMD/движки, безопасность,
конфигурацию, упаковку и полный CI перед land. GitHub по-прежнему запускает Full.

`-TestName` принимает точные имена файлов, без путей и масок; ошибка имени даёт
отказ до запуска тестов. Нельзя сочетать его с Quick. `-List` только перечисляет
выбранные наборы, без статики, дочерних процессов и логов.
В консоли и `run.json` указаны выбранные/обнаруженные наборы, Partial, времена,
оболочка и итог. `results.json` остаётся массивом, даже для одного теста.
Status=Running означает незавершённый прогон, а не успех. Это не снимок исходников:
не редактируйте дерево во время проверки; фиксация входов будет отдельным этапом.
Выбор меньшего набора сокращает обратную связь, но не ускоряет полный набор.

## Выпуск и аппаратура

[Release](../.github/workflows/release.yml) работает отдельно после ручной публикации
релиза владельцем: проверяет тег/версию и прикладывает ZIP и SHA-256. Описание
готовится в `docs/releases`. Workflow не заменяет проверку успешного CI коммита.
CMD находятся в корне ZIP, оба README поставляются вместе; `ci` не входит в ZIP.

После push владелец проверяет CI именно текущего коммита, затем выполняет `git land`.
Аппаратная приёмка отдельно: [правила и покрытие](../docs/testing.md).
