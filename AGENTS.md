# AGENTS.md

Правила для ИИ-агентов и участников **stm32-flasher**.
English: [maintenance](docs/en/maintenance.md).

## Порядок работы

1. Прочитайте [README](README.md), «Текущее состояние» и «Ближайшие шаги» в
   [TODO](TODO.md), затем Unreleased в [CHANGELOG](CHANGELOG.md).
   Рабочий цикл: [maintenance](docs/ru/maintenance.md); известные решения:
   [HOWTO](docs/ru/HOWTO.md) ([English](docs/en/HOWTO.md)).
2. Работайте в ветке `<агент>/<задача>` от актуального `main`: `claude/`,
   `codex/`, `gemini/`, `dev/`, … . Сохраняйте незавершённые изменения;
   подходящую текущую рабочую ветку можно продолжать.
   PR не используются. После проверок и push рабочей ветки владелец проверяет CI,
   затем выполняет `git land`: fast-forward в `main`, push и удаление рабочей ветки.
3. Коммиты: Conventional Commits на английском, подписанные GitHub Signing Key,
   без ссылок на сессии агентов. Не отключайте подпись при ошибке.
   Push, land, теги и релизы выполняет владелец; агент не запускает их без
   отдельного явного поручения. Команды и ограничения: HOWTO.
4. README, CHANGELOG и новые публичные памятки ведутся на русском и английском;
   обе версии обновляются вместе. ТЗ ведётся только на русском.
   Существующие `docs/user-guide.md` и `docs/testing.md` остаются русскими;
   их полный перевод не является условием каждой правки. Локальные исследования
   достаточно вести на русском.
5. Сохраняйте один самодостаточный `flash.cmd`; остальные CMD — тонкие обёртки.
   Не дробите рабочую логику на обязательные внешние файлы. Правки делайте узкими,
   сохраняйте совместимость Windows PowerShell 5.1 и PowerShell 7, RU/EN сообщений.
6. До изменений проверяйте `git status` и существующие правки. Не откатывайте их.
   Регрессии без оборудования: `tests/Test-*.ps1`; общий запуск:
   `tests/Invoke-Tests.ps1`. CI на Windows не заменяет аппаратную проверку.
7. Не коммитьте реальные серийники, персональные пути, прошивки HEX/BIN/ELF,
   резервные копии, логи оборудования, скачанные утилиты и кэши.
   Для публичных примеров используйте переменные или синтетические значения.
8. Новое повторно полезное решение добавляйте в RU/EN HOWTO вместе с изменением.
   Обновляйте TODO, CHANGELOG и затронутые требования/проверки ТЗ.
   После каждого этапа сообщайте результат, ограничения и следующий шаг.
   Указывайте проверенную текущую ветку и последовательность следующих Git-команд;
   явно отделяйте push от land, который выполняется только после успешного CI.

## Проведение исследований

1. Прочитайте локальные `docs/research/README.md`, `HISTORY.md` и сводку нужного
   исследования. Если материалов нет, сообщите об этом; не объявляйте прежние
   результаты повторно проверенными.
2. Используйте `docs/research/NN-short-name/` и одноимённую рабочую папку
   `tests/manual/NN-short-name/`. `NN` — две цифры, следующий порядковый номер;
   номера не переиспользуются. Корень проекта не служит стендом.
3. Для короткого исследования достаточно README с целью, планом, результатом
   и следующим шагом. При росте добавляйте `plan.md` и `results.md`; вопросы
   можно оставить в них. Отдельные ru/en, матрицы и файлы долга не обязательны.
4. До опыта запишите условия и ожидаемый результат; после — команды, факты,
   ограничения и ссылки на логи. Для аппаратного опыта фиксируйте оборудование,
   версии инструментов и SHA-256 входов локально. Сохраняйте исходные FAIL/ERROR.
   Обновляйте `docs/research/HISTORY.md`, новые записи сверху.
5. Сначала проверяйте без оборудования. До экспериментальной записи/стирания
   согласуйте плату и операции, сохраните и проверьте всю затрагиваемую память.
   После опыта, включая неудачный, восстановите и проверьте её. Если копия
   непригодна, не пишите; если восстановление невозможно, остановитесь и сообщите.
   Не снимайте защиту и не меняйте option bytes ради продолжения опыта.
6. Обе локальные папки игнорируются Git; не используйте `git add -f`.
   Принятые результаты переносите в код, штатные тесты и публичную документацию
   без ссылок на локальные отчёты. Прототип не становится частью CI автоматически.

Новые каталоги: lowercase-kebab-case. Публичные правила проверки:
[docs/testing.md](docs/testing.md); контракт и статус покрытия:
[ТЗ](docs/TECHNICAL_SPECIFICATION.md).
