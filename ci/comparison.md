# Сравнение worker на GitHub

**Русский** | [English](comparison.en.md)

Отдельный ручной workflow **CI Worker Comparison**, файл ci-compare.yml.
Обычный CI использует два worker; этот workflow отдельно сравнивает 1/2 worker.
Оборудование не используется.

## Первый результат

[Запуск 38186953080](https://github.com/ViacheslavMezentsev/stm32-flasher/actions/runs/38186953080)
на 4e4f41c: все восемь полных прогонов по 25 наборов успешны. Медианы 1/2 worker:
PS5.1 889.09/552.85 с (1.608x), PS7 735.26/486.08 с (1.513x).
Это основание для перехода обычного CI на два worker, не гарантия времени
или стабильности на всех Windows runners. Последующие push проверяют устойчивость.

## Запуск владельцем

1. Подписанный коммит и push рабочей ветки, успешный CI этого SHA, затем git land.
2. Дождаться CI main. В Actions выбрать CI Worker Comparison, Run workflow, main.
   Для первого ручного запуска workflow должен уже находиться в default branch:
   [правило GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
3. По завершении открыть Summary и скачать comparison-source,
   comparison-powershell, comparison-pwsh. Сохранить ссылку на run и SHA.

Публикация workflow не означает, что сравнение уже выполнено.

## Условия

- Один job создаёт WorkingTree-снимок checkout: ZIP, source, манифест SHA-256.
  Передача включает скрытые файлы. Обе оболочки проверяют одинаковый манифест.
- Два Windows jobs, PS5.1 и PS7. Внутри каждого одной VM последовательно
  выполняются **1, 2, 2, 1 worker**, без Quick и выбора подмножества.
  Сейчас полный комплект содержит 25 наборов; новый Test-*.ps1 попадёт автоматически.
- В каждом запуске прежний isolated-runner делает отдельные копии/TEMP/TMP,
  одинаковый прогрев, контроль процессов и целостности. Порядок наборов одинаков.
- Таймаут набора 600 с, запуска 1800 с. Обычная ошибка сохраняется, следующие
  попытки выполняются; отмена останавливает последовательность. Матрица
  не отменяет другую оболочку при ошибке.
- Эксперимент может занять около 40–60 минут на оболочку; это оценка, не гарантия.
  Лимит job 135 минут оставляет запас сверх четырёх бюджетов по 30 минут.
  Оболочки идут в отдельных jobs одновременно; расход runner-минут суммируется.
  Группа concurrency не допускает двух одновременно работающих экспериментов.

## Чтение результатов

comparison.json содержит SHA, версии/образ Windows/число CPU, исходные результаты
всех четырёх запусков, времена подготовки, выполнения и общего прохода.
Сравниваются медианы общего времени 1 и 2 worker, включая подготовку и контроль.
Это времена самого runner; checkout, передача артефактов и внешний запуск
оркестратора не включены. Полную длительность jobs смотрите отдельно.
Коэффициент = медиана(1) / медиана(2); значение меньше 1 означает замедление.
Вычисляется только при четырёх полных успешных запусках с совпадающими входами,
составом наборов и версиями. Ноль exit code без отчётов недостаточен.
Ошибка, изменение входа, пропуск/дубликат, оставшийся процесс или незавершённость
запрещают вывод об ускорении. Running не считается успешным результатом.

Артефакты хранятся 14 дней: исходный снимок отдельно, сводка и логи каждого
набора отдельно; генерируемые EXE/fixtures и копии исходников каждого worker
не загружаются. Загрузка логов запланирована через always(), в том числе при ошибке.
Аварийное прерывание job может оставить только частичные доказательства.

Порядок ABBA уменьшает влияние первого запуска, но не устраняет шум hosted VM.
Два измерения на режим недостаточны для устойчивой оценки разброса. Не сравнивайте
PS5.1 с PS7 как одинаковое оборудование: их VM разные. Это не сравнение с прежним
неизолированным runner и не основание автоматически менять CI по умолчанию.

После публикации результатов: оценить корректность, выигрыш и цену подготовки,
при необходимости повторить опыт; затем отдельно согласовать смену умолчания.
