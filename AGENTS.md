# AGENTS.md

Правила для агентов и участников. [English](docs/en/maintenance.md).

## Рабочий цикл

1. Начните с README, текущего состояния и ближайших шагов TODO, Unreleased
   в CHANGELOG. Архитектура и ограничения: [maintenance](docs/ru/maintenance.md);
   готовые команды: [HOWTO](docs/ru/HOWTO.md).
2. Проверьте `git status`. Работайте в `<агент>/<задача>` от актуального `main`
   (`codex/`, `claude/`, `gemini/`, `dev/`); подходящую текущую ветку можно продолжать.
   Сохраняйте чужие и незавершённые изменения. PR не используются.
3. Делайте узкие изменения с воспроизводящими тестами. Соблюдайте архитектурный
   контракт, совместимость и локализацию. Проверки: [ci](ci/README.md).
   CI не заменяет аппаратную проверку; запланированный тест не означает PASS.
4. Обновляйте TODO, затронутые требования и проверки ТЗ, RU/EN документацию вместе.
   Повторно полезные решения добавляйте в HOWTO. В CHANGELOG только категории
   «Добавлено», «Изменено», «Исправлено» (Added, Changed, Fixed); пустые не нужны.
   Заголовок выпуска: `## [X.Y.Z] - YYYY-MM-DD: краткий итог`.
5. Не включайте в Git персональные пути, реальные серийники, прошивки, резервные
   копии, аппаратные логи, скачанные инструменты и кэши. Новые каталоги называйте
   `lowercase-kebab-case`; публичные примеры должны быть обезличены.
6. Коммиты: английский Conventional Commits, подпись GitHub Signing Key,
   без ссылок на сессии агентов. При ошибке подписи не отключайте её.
   Push рабочей ветки, затем проверка CI, затем `git land` (fast-forward main,
   push, удаление ветки). Push, land, теги и релизы выполняет владелец;
   агенту нужно отдельное явное поручение. При расхождении веток остановитесь.
7. Завершая этап, сообщайте результат, ограничения, следующий шаг, проверенную
   текущую ветку и Git-команды. Отделяйте push от land после успешного CI.

## Исследования

1. Сначала прочитайте локальные `docs/research/README.md`, `HISTORY.md` и нужную
   сводку. Отсутствие материалов сообщайте; прежний результат не выдавайте за новый.
2. Используйте парные `docs/research/NN-name/` и `tests/manual/NN-name/`:
   следующий двухзначный номер, без повторного использования. Корень не стенд.
   Обе папки локальные и игнорируются Git; не применяйте `git add -f`.
3. Достаточно README с целью, условиями, ожидаемым результатом, командами,
   фактами, ограничениями и следующим шагом. При росте добавляйте plan/results.
   Ведите HISTORY новыми записями сверху, сохраняйте исходные FAIL/ERROR.
4. Сначала тестируйте без оборудования. До записи/стирания согласуйте плату
   и операции, сохраните и проверьте всю затрагиваемую память. После опыта,
   включая неудачный, восстановите и проверьте её. Непригодная копия запрещает
   запись; невозможность восстановления требует остановки и сообщения владельцу.
   Не снимайте защиту и не меняйте option bytes ради продолжения опыта.
5. Оборудование, версии и SHA-256 входов фиксируйте локально. Принятые результаты
   переносите в штатные тесты и публичные документы без личных данных и ссылок
   на локальные отчёты. Прототип не становится частью CI автоматически.
